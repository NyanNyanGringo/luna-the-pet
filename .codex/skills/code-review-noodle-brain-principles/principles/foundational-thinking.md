# Фундаментальное мышление

**Структурные решения**: модели данных, порядок фаз и инфраструктура, оптимизируются под ценность будущих опций. **Решения на уровне кода**: хелперы, абстракции и паттерны, оптимизируются под простоту.

«Переинженеринг» означает преждевременные решения, которые **закрывают двери**: лишние абстракции, спекулятивные фичи, слои косвенности. Правильно выбранная базовая структура данных, наоборот, **открывает двери**: она сохраняет ценность будущих вариантов.

- Плохая сложность: классы-хелперы для одноразовых операций, feature flags для гипотетических сценариев, абстракционные слои «на случай, если заменим X»
- Хорошая сложность: выбор структуры данных, которая соответствует реальным паттернам доступа, даже если прямо сейчас можно обойтись более простой

## Сначала структуры данных

Сначала сделай правильными структуры данных, и только потом пиши логику. Правильная структура делает последующий код очевидным. Неправильная мешает на каждом шаге.

- Рано определяй основные типы и позволь им вести архитектуру
- Прогоняй через предлагаемую структуру каждый паттерн доступа: чтение, запись, итерацию, lookup, сериализацию
- Выбирай структуры, которые соответствуют доминирующему паттерну доступа
- Позднее изменение структуры данных равно переписыванию; раннее часто укладывается в однострочный diff

На уровне кода простота сохраняет опции:
- **DRY на структурном уровне**: типы и модели данных, но три похожие строки кода лучше, чем преждевременная абстракция
- **Явность важнее хитрости**: хитрый код скрывает намерение, а значит закрывает двери
- **Без placeholder-файлов**: создавай файл только тогда, когда в нём есть реальный код
- **Хорошо тестируй**: проверяй поведение и крайние случаи, а не покрытие строк. См. [[principles/prove-it-works]].

**Следствие для конкурентности:** прежде чем разделять состояние между участниками, спроси: «Что произойдёт, если другой участник изменит это одновременно?» Если ответ не «ничего», изолируй.

## Сначала каркас

Если что-то помогает всей дальнейшей работе, делай это в первую очередь. Спроси: «Выиграет ли от этого каждая следующая фаза?» Если да, это каркас. Значит, это фаза 1, а не финальный штрих.

- CI, линтинг, тестовая инфраструктура → каркас
- Общие типы, конфигурация проекта → каркас

Это относится и к коммитам: выстраивай их ради максимальной ценности опций.
- Сначала инфраструктура и настройка, потом фичи; сначала тесты, потом исправления
- Держи коммиты маленькими и с одной целью
- Предпочитай коммиты, которые легко ревьюить, откатывать и выборочно переносить

Вычитание ([[principles/subtract-before-you-add]]) идёт перед созданием каркаса: сначала убери мёртвый вес, потом закладывай фундамент.

Спрашивай: «Это решение уменьшает мои будущие опции или сохраняет их?»
