# Сначала мигрируй вызывающий код, потом удаляй legacy API

**Принцип:** Если принято решение, что новый API является правильным дизайном, мигрируй вызывающий код и удаляй старый API в той же волне рефакторинга, а не сохраняй слои совместимости.

## Правило

- Не поддерживай legacy-пути API только потому, что на них ещё сидит внутренний код.
- Составь список вызывающих мест, мигрируй их и сразу удали старый API.
- Считай временные адаптеры исключением с жёстким сроком жизни, а не архитектурой по умолчанию.
- Обновляй тесты так, чтобы они проверяли новый контракт, и удаляй тесты, которые защищают только дорефакторинговые детали реализации.

## Когда это применимо

- Внешние пользователи не зависят от обратной совместимости
- Проект способен выдержать координированные ломающие изменения
- Новый API является частью инициативы по упрощению или рефакторингу

## Зачем

Поддержка и старого, и нового API создаёт двойную сложность, замедляет очистку и делает кодовую базу похожей на append-only-хранилище. Миграция вызывающего кода с последующим удалением legacy API сохраняет элегантность и усиливает вычитающий рефакторинг.
