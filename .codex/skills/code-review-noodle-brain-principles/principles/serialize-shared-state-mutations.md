# Сериализуй мутации общего состояния

**Принцип:** Когда параллельные участники делят изменяемое состояние, обеспечивай сериализацию структурно: через lock-файлы, последовательные фазы или эксклюзивное владение. Инструкций и договорённостей недостаточно для безопасности при конкурентности.

## Зачем

Параллельные записи в общее состояние: файлы, ветки, API, создают race condition'ы, которые проявляются не всегда, плохо воспроизводятся и дорого отлаживаются. Просьба к агентам или goroutine'ам «ходить по очереди» не работает: у них нет координационного механизма, кроме самой инструкции.

## Шаблон

Перед тем как разрешить любое параллельное выполнение: агентам, goroutine'ам, сессиям:

1. **Выяви общее изменяемое состояние.** Файлы, которые и читаются, и пишутся; ветки, в которые несколько участников пушат; API, которые одни описывают, а другие сразу потребляют.
2. **Если общее состояние есть, сериализуй доступ.** Используй lock-файлы, последовательные фазы или эксклюзивное владение.
3. **Если сериализация непрактична, убери разделение.** Дай каждому участнику свою копию: отдельный worktree, отдельные файлы, изолированную директорию состояния.

## Примеры

- Параллельные merge'и worktree приводили к двойной работе → исправлено через lock-файл `.worktrees/.merge-lock`
- Параллельные менеджеры, разделяющие контракт API, изобретали конфликтующие версии → исправление: последовательные фазы, сначала producer, потом consumer
- Неблокирующая отправка в заполненный канал теряла итог выключения → причина в общем канале без сериализации
- Lock-файл merge для worktree использует PID-основанное обнаружение устаревших блокировок → структурное обеспечение взаимного исключения
