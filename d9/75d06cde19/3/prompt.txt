# План исправлений по итогам ревью

  ## Summary

  Исправить 4 проблемы: 2 критичные по консистентности доменных данных и 2 средние по корректности выборок и ограничению объёма read-tool.
  Цель: запретить сохранение некорректных интервалов, сделать контракт active_only фактически корректным во всех вызовах и вернуть bounded-
  поведение для истории кормлений.

  ## Key Changes

  ### 1. Хронология диет

  - В nutrition_service.add_diet_record() добавить обязательную проверку end_date >= start_date, если end_date передан явно.
  - Эту проверку выполнять всегда, независимо от наличия open_diets.
  - Сохранить текущую проверку пересечения с открытой диетой, но выполнять её после базовой валидации интервала.
  - Текст ошибки сделать доменным и однозначным: отдельно для “обратной хронологии” и отдельно для “пересечения с текущей диетой”.

  ### 2. Хронология heat cycle

  - В health_service.add_heat_cycle() добавить обязательную проверку end_date >= start_date, если end_date передан.
  - В alembic-миграцию добавить DB-level защиту CHECK (end_date IS NULL OR end_date >= start_date) для heat_cycle.
  - Если проект допускает правку уже созданной миграции до merge, менять существующую миграцию; если миграция уже считается опубликованной,
    оформить отдельную follow-up миграцию с ALTER TABLE ... ADD CONSTRAINT.
  - Ошибка на уровне сервиса и ограничение на уровне БД должны выражать один и тот же инвариант.

  ### 3. Корректность active-only для лекарств

  - В health_service.get_medications() сделать фильтрацию просроченных записей при active_only=True обязательной, а не зависящей от внешнего
    today=None.
  - Дефолт выбора даты: если today не передан, использовать текущую UTC date внутри сервиса.
  - Не менять текущую semantics для записей без end_date: они остаются активными при is_active=True.
  - Не менять сортировку и shape ответа.
  - Проверить вызывающие места, где get_medications(active_only=True) вызывается без today, и зафиксировать тестом, что теперь они получают
    только реально активные записи.

  ### 4. Ограничение объёма get_feeding_history

  - В nutrition_service.get_feeding_entries() всегда применять limit, даже когда заданы обе границы периода.
  - Дефолт оставить текущим 20, если явный limit не вводится в tool schema.
  - В tool_handlers._handle_get_feeding_history() не менять интерфейс инструмента, но опираться на bounded-поведение сервиса.
  - Если текущий продуктовый сценарий требует возвращать “весь период”, это должно оформляться отдельным explicit-параметром; в рамках этого
    исправления такого поведения не оставлять.
