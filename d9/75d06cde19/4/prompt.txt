## План исправлений по ревью

  ### Summary

  Исправление делится на 3 блока: выровнять контракт document_type между tool schema, handler, сервисом и тестами; перенести инвариант
  активности Medication из handler в доменный слой; усилить boundary-валидацию новых function-calling tools через enum, чтобы невалидные
  значения отсеивались до вызова сервисов.

  ### Key Changes

  - Document
      - Выбрать один канонический словарь document_type и использовать его во всех слоях без исключений.
      - Рекомендованный вариант: оставить канонические значения passport|analysis|certificate|other как единственный публичный и внутренний
        контракт.
      - Обновить описание add_document/get_documents, чтобы тексты не обещали русские свободные типы вроде справка и рентген.
      - В tool_handlers не добавлять скрытую нормализацию старых русских значений, если цель именно завершить миграцию; вместо этого
        мигрировать все тесты и внутренние callers на каноничные значения.
      - Если обратная совместимость всё же обязательна, явно зафиксировать временный mapping в одном месте и покрыть его отдельными тестами,
        но срок жизни такого adapter-path должен быть ограничен.
  - Medication
      - Перенести правило синхронизации is_active и end_date в health_service.add_medication, чтобы оно работало для любого caller, а не
        только для agent handler.
      - Зафиксировать доменный инвариант: препарат считается завершённым, если end_date < effective_today; при создании записи с таким
        end_date сервис должен выставлять is_active=False.
      - Убрать дублирующую бизнес-логику из handler или свести её к простому пробросу аргументов.
      - В grouped-read для get_medications(active_only=False) группировать записи по тому же правилу “активности”, что и в сервисе, а не
        только по сырому is_active.
      - Рекомендованный вариант: вычислять “effective active” через ту же пару полей is_active + end_date относительно workspace_today,
        чтобы один и тот же препарат не попадал в разные состояния в разных ответах.
      - Дополнительно закрыть кейс одинаковой даты начала диеты, если команда решит включить и этот сигнал: не позволять автозакрытию
        открытой диеты выставлять end_date < start_date; при new_start_date == current_start_date либо отклонять запись, либо явно задавать
        правило merge/replace. Рекомендованный вариант: отклонять как конфликт хронологии.
  - Tool schema / boundary validation
      - Добавить enum в JSON-схемы для всех новых полей с закрытым набором значений:
          - measurement_type
          - vet_visit.status
          - mood
          - appetite
          - при необходимости проверить, что record_type и document_type уже оформлены тем же образом и не расходятся с сервисами.
      - Считать tools.py единственной boundary-спецификацией для function calling: если сервис валидирует закрытое множество, schema обязана
        повторять это множество дословно.
      - Синхронизировать тексты description с реальными enum, чтобы модель не получала конфликтующие подсказки.

  ### Test Plan

  - Обновить unit-тесты document:
      - handler и tool-definition используют только каноничные document_type;
      - сервис отвергает неканоничные значения;
      - при выбранном варианте с временным mapping добавить явные тесты на mapping и отдельный TODO на его удаление.
  - Добавить тесты на Medication:
      - прямой вызов health_service.add_medication с прошедшим end_date создаёт запись с is_active=False;
      - grouped-read относит просроченный препарат в завершённые даже если в БД is_active=True;
      - active_only=True и обычный get_medications не противоречат друг другу на одном и том же наборе данных.
  - Добавить schema-тесты:
      - новые tool definitions содержат точные enum для закрытых словарей;
      - значения enum совпадают с доменными whitelist в сервисах.
  - Если включать фикс диеты:
      - тест на new_start_date == current_start_date и выбранное поведение;
      - тест, что сервис больше не может создать запись с end_date < start_date через автозакрытие.

  ### Assumptions

  - Базовое решение: не сохранять legacy-русские типы документов как часть публичного контракта; завершить миграцию на каноничные значения.
  - Базовое решение: доменный слой, а не handler, владеет инвариантами жизненного цикла Medication.
  - Базовое решение: для function-calling schema должна быть строгой и повторять сервисные ограничения, а не оставлять их “на потом” в
    runtime.
