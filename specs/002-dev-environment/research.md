# Исследование: 002-dev-environment (Docker-Only)

**Дата**: 2026-03-10  
**Ветка**: `002-dev-environment`

## R-001: Переключение polling/webhook через `APP_ENV`

**Решение**: Сохранить существующий контракт приложения:
- `APP_ENV=dev` -> polling
- `APP_ENV=prod` -> webhook

**Обоснование**:
- Логика уже реализована и покрыта unit-тестами lifecycle.
- Для Docker-only задачи требуется синхронизация orchestration и документации, а не изменение бизнес-логики старта.

---

## R-002: Автоматизация миграций через отдельный сервис

**Решение**: Добавить `migrate` сервис в оба compose-файла.

**Обоснование**:
- Убирает ручной шаг `docker compose exec app alembic upgrade head`.
- Гарантирует, что `app` стартует только на актуальной схеме БД.
- Устраняет частый race condition при первом запуске на пустом volume.

---

## R-003: Корректный `postgres.healthcheck`

**Решение**: В healthcheck явно указывать БД через `-d`.

**Обоснование**:
- `pg_isready -U luna` может проверять БД с именем пользователя (`luna`) и давать ложный `FATAL`.
- Явные проверки:
  - dev: `pg_isready -U luna -d luna_dev_db`
  - prod: `pg_isready -U luna -d luna_db`

---

## R-004: Docker-only DX для dev

**Решение**: Основной dev-сценарий фиксируется как `docker compose -f docker-compose.dev.yml up` (foreground).

**Обоснование**:
- Сохраняется удобство отладки: live-логи и hot reload.
- Устраняется расхождение между локальным и контейнерным путями запуска приложения.

---

## R-005: Env-слой и документация

**Решение**:
- dev -> `.env.dev`
- prod -> `.env.prod`
- `.env.example` оставить как legacy fallback для Settings, но убрать из happy path.

**Обоснование**:
- Явное разделение окружений снижает риск запуска с неверными параметрами.
- Документация становится однозначной: приложение запускается только через Docker Compose.
