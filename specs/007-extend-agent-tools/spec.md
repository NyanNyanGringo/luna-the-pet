# Feature Specification: Расширение базы данных и инструментов AI-агента

**Feature Branch**: `007-extend-agent-tools`
**Created**: 2026-03-17
**Status**: Draft
**Input**: User description: "Расширить базу данных и инструменты AI-агента: новые таблицы, инструменты чтения, расширение полей, обновление system prompt"

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Чтение существующих данных о питомце (Priority: P1)

Пользователь спрашивает бота: «Сколько Луна весила в январе?», «Какие прививки у Луны?», «Что за лекарства она принимает?», «Покажи последние заметки», «Чем кормили вчера?», «Какой сейчас корм?». Бот использует инструменты чтения и отвечает структурированной информацией из базы данных.

**Why this priority**: Без инструментов чтения бот — «чёрная дыра»: данные записываются, но не возвращаются. Чтение критически важно для полезности бота.

**Independent Test**: Записать несколько весов/прививок/лекарств/заметок/кормлений/диет, затем спросить бота — ответ должен содержать ранее записанные данные.

**Acceptance Scenarios**:

1. **Given** у питомца записано 5 измерений веса, **When** пользователь спрашивает «покажи историю веса», **Then** бот возвращает список записей с датами и значениями в хронологическом порядке
2. **Given** у питомца есть активные и завершённые лекарства, **When** пользователь спрашивает «какие лекарства принимает?», **Then** бот возвращает список с разделением на активные и завершённые
3. **Given** у питомца записаны вакцинации с датой следующей прививки, **When** пользователь спрашивает «когда следующая прививка?», **Then** бот показывает ближайшую плановую дату
4. **Given** у питомца записано 20 заметок, **When** пользователь спрашивает «покажи заметки», **Then** бот возвращает последние 10 заметок (по умолчанию) с датами
5. **Given** у питомца записаны кормления за неделю, **When** пользователь спрашивает «чем кормили вчера?», **Then** бот показывает записи кормлений за запрошенный период
6. **Given** у питомца есть активная диета, **When** пользователь спрашивает «какой сейчас корм?», **Then** бот показывает текущую диету (запись без end_date)

---

### User Story 2 — Расширение полей записи в существующих инструментах (Priority: P1)

Пользователь говорит: «Поставили прививку Нобивак, серия AB123, следующая через год, ветеринар Иванов». Бот записывает все поля, а не только название и дату. Аналогично для лекарств, диеты, кормлений и профиля питомца.

**Why this priority**: Без полных полей записанные данные неполны и бесполезны при чтении. Эта задача тесно связана с P1 (чтение) — читать нечего, если данные записаны частично.

**Independent Test**: Передать боту все поля при записи вакцинации/лекарства/диеты/кормления/профиля, затем прочитать запись и убедиться, что все поля сохранены.

**Acceptance Scenarios**:

1. **Given** пользователь сообщает о прививке со всеми деталями, **When** агент вызывает add_vaccination, **Then** записываются: vaccine_name, date, next_date, vet_name, batch_number, notes
2. **Given** пользователь сообщает о лекарстве с частотой и сроками, **When** агент вызывает add_medication, **Then** записываются: name, dosage, frequency, start_date, end_date, last_given_date, notes
3. **Given** пользователь описывает новую диету с типом корма, **When** агент вызывает add_diet, **Then** записываются: food_brand, food_type, start_date, end_date, notes
4. **Given** пользователь сообщает о кормлении с размером порции, **When** агент вызывает add_feeding, **Then** записываются: food_description, fed_at, portion_size
5. **Given** пользователь хочет обновить профиль питомца, **When** агент вызывает update_pet, **Then** можно обновить: breed, birth_date, gender, is_neutered, origin_story, blood_type, chip_number, vet_contact

### User Story 3 — Запись и чтение медицинских записей (Priority: P2)

Пользователь говорит: «Луна заболела — расстройство желудка с 15 марта» или «Был плановый осмотр у ветеринара». Бот записывает медицинскую запись (болезнь, осмотр, операция) и может позже показать историю.

**Why this priority**: Таблица MedicalRecord уже существует в БД, но у агента нет инструмента для работы с ней. Это «мёртвая» таблица, которую нужно оживить.

**Independent Test**: Попросить бота записать болезнь/осмотр/операцию, затем спросить «какие болезни были?» — бот должен вернуть записи.

**Acceptance Scenarios**:

1. **Given** пользователь описывает болезнь питомца, **When** агент вызывает add_medical_record с типом «illness», **Then** создаётся запись с title, description, date, vet_name
2. **Given** пользователь сообщает о плановом осмотре, **When** агент вызывает add_medical_record с типом «checkup», **Then** создаётся запись с date, vet_name, description
3. **Given** пользователь сообщает об операции, **When** агент вызывает add_medical_record с типом «surgery», **Then** создаётся запись с title, description, date, resolved_date, vet_name
4. **Given** у питомца есть медицинские записи, **When** пользователь спрашивает «покажи историю болезней», **Then** бот возвращает записи с возможностью фильтрации по типу

---

### User Story 4 — Новые таблицы: измерения, визиты, самочувствие, документы, течка (Priority: P2)

Пользователь записывает через бота: температуру/пульс/дыхание, визиты к ветеринару, ежедневное самочувствие, ссылки на медицинские документы, циклы течки. И может потом запросить эту информацию.

**Why this priority**: Новые сущности расширяют функциональность бота для более полного ухода за питомцем, но не блокируют основные сценарии.

**Independent Test**: Для каждой из 5 новых таблиц — записать данные через бота, затем запросить их и убедиться в корректности.

**Acceptance Scenarios**:

1. **Given** пользователь измерил температуру питомца, **When** агент вызывает add_measurement, **Then** создаётся запись с типом «temperature», значением, единицей измерения и датой
2. **Given** пользователь записывается к ветеринару, **When** агент вызывает add_vet_visit, **Then** создаётся запись со статусом «planned», клиникой, причиной и датой
3. **Given** пользователь описывает самочувствие питомца, **When** агент вызывает add_mood_log, **Then** создаётся запись с настроением, аппетитом, датой и заметками
4. **Given** пользователь хочет сохранить ссылку на анализы, **When** агент вызывает add_document, **Then** создаётся запись с типом документа, URL, датой выдачи и описанием
5. **Given** у некастрированной самки началась течка, **When** агент вызывает add_heat_cycle, **Then** создаётся запись с датой начала и заметками
6. **Given** у питомца есть записи измерений за месяц, **When** пользователь спрашивает «покажи температуру за последнюю неделю», **Then** бот возвращает записи за указанный период
7. **Given** у питомца есть запланированный визит, **When** пользователь спрашивает «когда следующий приём?», **Then** бот показывает ближайший запланированный визит

---

### User Story 5 — Обновлённый system prompt: агент умеет отвечать на вопросы (Priority: P1)

Пользователь задаёт вопрос: «Когда последний раз глистогонили?», «Что было с Луной на прошлой неделе?», «Покажи сводку здоровья». Агент понимает, что нужно использовать инструменты чтения и вернуть данные, а не просто записывать.

**Why this priority**: Без обновления промпта агент не будет знать, что может читать данные, и продолжит только записывать. Это ключевое изменение, которое «включает» все новые инструменты чтения.

**Independent Test**: Задать боту вопросы о данных питомца — бот должен использовать инструменты чтения и ответить содержательно.

**Acceptance Scenarios**:

1. **Given** system prompt обновлён, **When** пользователь задаёт вопрос о данных питомца, **Then** агент использует соответствующий инструмент чтения и формирует ответ
2. **Given** system prompt обновлён, **When** пользователь просит сводку, **Then** агент комбинирует данные из нескольких инструментов чтения

---

### Edge Cases

- Что происходит, если у питомца нет записей при запросе чтения? Бот сообщает, что данных пока нет
- Что происходит при запросе истории за период, в котором нет данных? Бот сообщает, что за указанный период записей нет
- Что происходит при попытке записать течку для кастрированного питомца? Бот предупреждает, что питомец отмечен как кастрированный
- Что происходит при запросе «последние N заметок», если N больше общего количества? Возвращаются все доступные заметки
- Что происходит при записи измерения с некорректным типом? Инструмент принимает только допустимые типы (temperature, pulse, respiration)

## Requirements *(mandatory)*

### Functional Requirements

#### Инструменты чтения для существующих данных

- **FR-001**: Система ДОЛЖНА предоставить инструмент чтения истории веса питомца с возвратом записей (вес, дата) в хронологическом порядке
- **FR-002**: Система ДОЛЖНА предоставить инструмент чтения вакцинаций питомца с возвратом всех полей, включая дату следующей прививки
- **FR-003**: Система ДОЛЖНА предоставить инструмент чтения лекарств с разделением на активные (is_active=true) и завершённые
- **FR-004**: Система ДОЛЖНА предоставить инструмент чтения заметок с параметром limit (по умолчанию 10), сортировка по дате создания (новые первые)
- **FR-005**: Система ДОЛЖНА предоставить инструмент чтения истории кормлений за указанный период (параметры: start_date, end_date; по умолчанию — последние 7 дней)
- **FR-006**: Система ДОЛЖНА предоставить инструмент чтения текущей диеты (записи без end_date или с end_date в будущем)

#### Медицинские записи

- **FR-007**: Система ДОЛЖНА предоставить инструмент записи медицинских записей с параметрами: pet_name, record_type (illness/checkup/surgery), title, description, date, resolved_date, vet_name
- **FR-008**: Система ДОЛЖНА предоставить инструмент чтения медицинских записей с опциональной фильтрацией по типу записи (record_type)

#### Новые таблицы и инструменты

- **FR-009**: Система ДОЛЖНА хранить измерения питомца (тип: temperature/pulse/respiration, значение, единица измерения, дата) и предоставить инструменты записи и чтения
- **FR-010**: Система ДОЛЖНА хранить визиты к ветеринару (клиника, причина, дата, статус: planned/completed, заметки) и предоставить инструменты записи и чтения
- **FR-011**: Система ДОЛЖНА хранить записи самочувствия (настроение: excellent/good/normal/poor, аппетит: good/reduced/none, дата, заметки) и предоставить инструменты записи и чтения
- **FR-012**: Система ДОЛЖНА хранить ссылки на медицинские документы (тип, URL, дата выдачи, описание) и предоставить инструменты записи и чтения
- **FR-013**: Система ДОЛЖНА хранить записи о течке (дата начала, дата окончания, заметки) и предоставить инструменты записи и чтения

#### Расширение существующих инструментов записи

- **FR-014**: Инструмент add_vaccination ДОЛЖЕН принимать дополнительные опциональные параметры: next_date, vet_name, batch_number, notes
- **FR-015**: Инструмент add_medication ДОЛЖЕН принимать дополнительные опциональные параметры: frequency, end_date, last_given_date, notes
- **FR-016**: Инструмент add_diet ДОЛЖЕН принимать дополнительные опциональные параметры: food_type, end_date, notes
- **FR-017**: Инструмент add_feeding ДОЛЖЕН принимать дополнительный опциональный параметр: portion_size
- **FR-018**: Инструмент update_pet ДОЛЖЕН принимать дополнительные опциональные параметры: origin_story, blood_type, chip_number, vet_contact

#### System prompt

- **FR-019**: System prompt ДОЛЖЕН сообщать агенту, что он может как записывать, так и читать данные о питомцах — отвечать на вопросы, показывать историю, выводить сводки

### Key Entities

- **Measurement (Измерение)**: Разовый замер физиологического параметра питомца. Привязан к питомцу. Атрибуты: тип (temperature/pulse/respiration), значение, единица измерения, дата
- **VetVisit (Визит к ветеринару)**: Запланированный или состоявшийся визит. Привязан к питомцу. Атрибуты: клиника, причина, дата, статус (planned/completed), заметки
- **MoodLog (Самочувствие)**: Ежедневное наблюдение за состоянием питомца. Привязан к питомцу. Атрибуты: настроение (excellent/good/normal/poor), аппетит (good/reduced/none), дата, заметки
- **Document (Документ)**: Ссылка на медицинский документ. Привязан к питомцу. Атрибуты: тип документа, URL, дата выдачи, описание
- **HeatCycle (Течка)**: Запись о цикле течки для некастрированных самок. Привязан к питомцу. Атрибуты: дата начала, дата окончания, заметки

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь может получить ответ на любой вопрос о ранее записанных данных питомца (вес, прививки, лекарства, заметки, кормления, диета, медицинские записи) через чат-бота
- **SC-002**: При записи вакцинации, лекарства, диеты, кормления и обновлении профиля сохраняются все поля, которые пользователь упомянул в сообщении
- **SC-003**: Пользователь может записывать и просматривать данные по 5 новым категориям: измерения, визиты к ветеринару, самочувствие, документы, течка
- **SC-004**: Агент самостоятельно определяет, нужно ли записать данные или прочитать их, на основе контекста сообщения пользователя

## Assumptions

- Все новые таблицы следуют существующему паттерну: привязка к pet_id через FK, поле recorded_by для аудита, created_at с server_default
- Единицы измерения для Measurement: °C для температуры, уд/мин для пульса, вд/мин для дыхания — хранятся как строковые значения
- Инструменты чтения возвращают текстовое представление данных (как существующий get_pet_profile), а не JSON
- Значения enum (mood, appetite, measurement_type, visit_status) хранятся как строки, не как PostgreSQL ENUM
- Для истории кормлений период по умолчанию — последние 7 дней, если пользователь не указал конкретный период
- Все новые инструменты интегрируются в существующую систему аудита (ChangeLog)
- Новые таблицы требуют Alembic-миграции
